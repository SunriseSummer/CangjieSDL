# Thunder Fighter 教程：建立实时游戏循环

这个 800×600 的纵版射击小游戏把 Calculator 的“事件后重绘”推进为“每帧更新世界”。玩家可以持续
移动和开火，敌机会不断生成，子弹、碰撞、生命、粒子与 HUD 都由同一条帧循环协调。

![雷霆战机运行效果](../.images/thunder.png)

## 学完以后

你应该能够：

- 用秒为单位的 `dt` 编写不绑定显示器刷新率的移动、冷却和寿命逻辑；
- 把 `KeyDown` / `KeyUp` 边沿事件转换成每帧可读取的持续输入状态；
- 用 `GameState` 聚合世界数据，用系统函数按明确顺序推进状态；
- 在遍历中安全删除失效实体，并用 AABB 完成基础碰撞检测；
- 按背景、实体、特效和 HUD 的视觉层次组织一帧绘制。

开始前最好已理解 [Calculator 教程](../calculator/)中的事件循环、状态与渲染分离；不要求有游戏开发经验。

## 运行和操作

从仓库根目录执行：

```powershell
Set-Location examples\thunder
cjpm build
cjpm run
```

- 方向键移动。
- 按住空格连续开火；开火时移动速度降低，便于精确走位。
- 三条生命耗尽后按空格重新开始。
- `Esc` 退出。

如果程序提示找不到 SDL 动态库，请先阅读[示例总览的构建和运行说明](../README.md#构建和运行)。

## 先建立整体模型

实时游戏不应在每个事件分支里直接移动和绘制对象。这个示例把一帧分成四个阶段：

```text
计算 dt → 取空事件队列 → update(state, dt) → draw(state)
              │                    │                 │
          更新 InputState      推进世界并结算碰撞    只表现当前状态
```

事件描述“刚刚发生了什么”，`InputState` 描述“现在按住了什么”，`GameState` 描述“当前世界是什么样”。
这三类信息的时间语义不同，分开后，移动、连发和动画才不会依赖系统的按键重复频率。

| [`src/collision.cj`](src/collision.cj) | 命中检测、扣命和得分 | 哪个系统负责移除和结算？ |

是参数词典，需要时查阅即可。

## 第一课：正确理解 `dt`

[`runGame`](src/loop.cj) 通过两次 `window.ticks()` 的差值计算本帧经过的毫秒数，再除以 1000 得到秒。
移动遵循同一个公式：

```text
本帧位移 = 每秒速度 × dt
```

因此 60 Hz 下较大的单帧位移和 144 Hz 下较小的单帧位移，会在相同真实时间内累积出近似相同距离。
同样的规则也用于开火冷却、无敌时间、粒子寿命和敌机生成计时。

这里采用的是**有上限的可变时间步长**，不是固定时间步长。`dt` 被限制在 0 到 0.05 秒之间，避免拖动窗口、
断点调试或系统卡顿后出现一次巨大的位移。截断能限制异常，但不会自动解决高速物体穿透；速度更高或碰撞更
复杂时，应继续考虑固定步长、子步进或扫掠碰撞。

## 第二课：从按键事件得到持续输入

[`setKey`](src/loop.cj) 不直接移动战机，只在按下和抬起时修改 `InputState` 中的布尔字段。随后
[`updatePlayer`](src/systems.cj) 每帧读取这些字段并积分位移。

这解决了两个常见问题：

- 移动速度不再依赖操作系统何时产生重复按键事件；
- 同一帧可以组合多个按键，例如同时向左和向上移动。

开火也使用持续状态，但增加 `cooldown` 作为节流器。按住空格时，冷却归零才调用 `fire`，随后重新装填
`Ship.FIRE_COOLDOWN`。输入意图和行为频率由此分离。

## 第三课：用状态和系统推进世界

[`GameState`](src/model.cj) 聚合随机数生成器、输入、玩家以及所有实体集合。它是当前一局游戏的事实来源。
[`update`](src/systems.cj) 明确规定系统顺序：

1. 星空和粒子始终更新，让结算画面仍保持动态；
2. 游戏结束时停止玩家、子弹、敌机和碰撞更新；
3. 正常阶段依次更新玩家、子弹、敌机；
4. 最后统一进行碰撞与生命结算。

这种“状态保存数据、系统推进数据”的结构比让每个实体自行控制主循环更容易观察顺序，也便于以后加入暂停、
回放或无窗口测试。

所有速度、数量和边界都集中在 [`config.cj`](src/config.cj) 的语义结构中。例如，难度曲线只由初始生成间隔、
最小间隔和分数系数共同决定。调参时不必在模拟和渲染文件中寻找魔法数字。

## 第四课：安全维护动态实体集合

子弹、敌机和粒子使用 `ArrayList` 保存。更新时从最后一个下标向前遍历，遇到越界、命中或寿命结束的实体就
立即删除。

倒序遍历的原因很具体：删除位置 `i` 后，右侧元素会前移，但这些元素已经处理过；尚未处理的较小下标保持
不变。如果正序删除，下一个元素前移到当前下标后，很容易被跳过。

在 [`collision.cj`](src/collision.cj) 中，子弹命中会先移除子弹；敌机生命归零后由 `destroyEnemy` 统一生成
粒子、移除敌机并加分。把一项结算的副作用放在一个函数中，可避免不同碰撞路径只完成一半工作。

## 第五课：碰撞形状不必等于视觉形状

[`intersects`](src/util.cj) 使用轴对齐包围盒（AABB）判断两个矩形是否重叠。它计算成本低，适合本示例的
矩形实体。

玩家的 `bounds()` 比战机视觉矩形小。于是机翼边缘擦过敌机不会立即扣命，画面仍然紧张，但操作更公平。
受击后 `invincible` 暂时阻止再次碰撞；渲染层根据同一个计时值让战机闪烁。这体现了一个重要边界：
“是否可受击”属于模拟规则，“如何提示无敌”属于视觉表现。

## 第六课：绘制顺序就是视觉层级

[`draw`](src/render.cj) 从远到近依次绘制天空和网格、星空、子弹、敌机、玩家、粒子与 HUD。即时渲染没有
自动层级树，后绘制的内容覆盖先绘制的内容，因此函数调用顺序就是清晰、可检查的图层协议。

示例还展示了几种基础图元的组合：

- 外扩矩形加圆角填充形成子弹光晕；
- 矩形、圆形和粗线组合出敌机与战机；
- 粒子透明度按剩余寿命线性衰减；
- 圆角填充、描边和文字居中组成 HUD 与结算面板。

所有绘制都位于 `beginScene` 与 `endScene` 之间，随后由 `present` 提交到窗口。

## 动手练习

### 练习 1：只通过配置改变手感

在 [`config.cj`](src/config.cj) 中修改玩家速度、开火冷却和敌机生成间隔。验收时确认无需改动系统函数，
且高低刷新率下速度仍按真实时间保持一致。

### 练习 2：加入多层视差星空

给星星增加层级或按速度划分远近层；远层更暗更慢，近层更亮更快。验收标准是至少同时出现两种明显速度，
星星越过底部后仍回收到正确层级。

### 练习 3：增加重型敌机

让新敌机拥有多点生命，并把“受击但未摧毁”和“摧毁”表现分开。你需要同时修改模型、生成、碰撞和绘制，
但不应改动主循环。验收时确认每发子弹只扣一次生命，最终一击只结算一次分数。

### 练习 4：显示性能数据

使用 `sdl.system.PerformanceClock` 统计帧耗时，在 HUD 中显示 FPS。把采样和格式化放在状态/更新侧，渲染层只
读取结果；分别在静止画面和大量粒子爆炸时观察数据。

## 验证清单

- 按住和松开方向键时，移动立即开始和停止；
- 60 Hz 与高刷新率显示器上的速度和冷却近似一致；
- 子弹、敌机和粒子离开生命周期后不会继续留在集合中；
- 擦过战机外缘不误判，连续重叠不会绕过无敌时间重复扣命；
- 三条生命耗尽后模拟停止，空格可完整重置一局；
- 关闭窗口和按 `Esc` 都能正常结束进程。

源码修改后先执行 `cjpm build`，再运行游戏完成输入和视觉验收。要继续学习多包分层、纹理资源、世界坐标与
骨骼动画，请进入 [Neon Commando 教程](../contra/)。
